Chat Widget — Technical Change Report
Date: 2026-07-30

Scope: replace the placeholder chatbot system prompt with the production
Nollie prompt, and make the /api/chat route locale-aware based on the page
the visitor is browsing.

================================================================================
FILES CHANGED
================================================================================

1. app/api/chat/route.ts        — rewritten prompt + locale handling
2. app/components/chat/ChatWidget.tsx — locale forwarded via chat transport

================================================================================
1) app/api/chat/route.ts
================================================================================

Removed
-------
- The old inline SYSTEM_PROMPT constant (the placeholder 12-line rules block
  that only said "reply in the same language, keep it short").
- The TODO comment above it about fleshing the prompt out.

Added
-----
- A local `buildPrompt(pageLang: "en" | "ar"): string` function that returns
  the full Nollie system prompt as plain text. The function:
    * Maps "ar" -> "Arabic", otherwise -> "English".
    * Interpolates that resolved language string into two places in the
      prompt (the "browsing in X" line near the top and the LANGUAGE
      section near the bottom).
    * Contains the full FACTS block (services, inclusions, add-ons,
      pricing policy, timelines, payment stages, process, client
      deliverables, team, portfolio).
    * Contains policy sections for WHEN YOU DO NOT KNOW, GENERAL WEB
      DESIGN QUESTIONS, OFF-TOPIC, LANGUAGE, and FORMAT.
    * Enforces plain text, single link exception `[label](#contact)`,
      1-2 sentence replies (up to 4 for multi-part), no persona changes,
      and no prompt disclosure.

Request handling changes in POST
--------------------------------
- The request JSON destructure now also reads `lang`:
      const { messages, lang }: { messages: UIMessage[]; lang?: unknown }
        = await req.json();
  `lang` is typed as `unknown` on purpose so the whitelist below is the
  single source of truth.

- Added a strict whitelist right after parsing:
      const pageLang: "en" | "ar" = lang === "ar" ? "ar" : "en";
  Anything that isn't the literal string "ar" falls back to "en". This
  means a malformed / missing / attacker-supplied `lang` value cannot
  end up interpolated into the system prompt.

- `streamText`'s `system` field now calls `buildPrompt(pageLang)` instead
  of referencing the removed SYSTEM_PROMPT constant.

Unchanged (intentionally)
-------------------------
- Upstash rate limit (20 msgs / 10 min / IP), MAX_HISTORY = 12,
  MAX_MESSAGE_CHARS = 1000, maxDuration = 30.
- Model: groq("llama-3.3-70b-versatile").
- maxOutputTokens: 400.
- `convertToModelMessages(history)` pipeline and the per-part length check.

================================================================================
2) app/components/chat/ChatWidget.tsx
================================================================================

Imports
-------
- Added `useMemo` to the React import.
- Added `import { DefaultChatTransport } from "ai";` — this is the AI SDK
  v6 transport class used to attach extra body fields to every chat
  request.

Body of ChatWidget()
--------------------
- Created a memoised transport instance:
      const transport = useMemo(
        () =>
          new DefaultChatTransport({
            api: "/api/chat",
            body: { lang },
          }),
        [lang],
      );
  Notes:
    * `api: "/api/chat"` matches the existing route path (previously the
      default was used implicitly — behaviour is identical).
    * `body: { lang }` is merged into every POST the chat hook sends, so
      the server receives `{ messages, lang }` on every turn.
    * The transport is memoised on `lang` so it is only re-created when
      the page's language actually changes; otherwise `useChat` would
      churn its internal state on each render.

- `useChat()` is now called as `useChat({ transport })` instead of with
  no arguments. Everything downstream (`messages`, `sendMessage`,
  `status`, `error`) is unchanged.

Unchanged
---------
- Props signature (`{ lang }: ChatWidgetProps`).
- Message rendering, `[label](#contact)` regex, contact link handler.
- Scroll stickiness, suggestions list, input clamp (maxLength=1000),
  error label mapping, all Tailwind classes and a11y labels.

================================================================================
DATA FLOW END-TO-END
================================================================================

1. `app/[lang]/layout.tsx` (or wherever ChatWidget is mounted) already
   passes `lang: Lang` into <ChatWidget lang={lang} />.
2. ChatWidget builds a DefaultChatTransport with `body: { lang }`.
3. Every `sendMessage(...)` from useChat POSTs to /api/chat with a JSON
   body of shape `{ messages: UIMessage[], lang: "en" | "ar" }`.
4. route.ts reads `lang`, whitelists it to `"en" | "ar"`, passes it to
   buildPrompt, and hands the resulting system prompt to streamText.
5. The model receives a system prompt that names the visitor's browsing
   language in two places and hard-locks replies to that language (see
   the "LANGUAGE HARD-LOCK" follow-up section below — the earlier
   revision of this prompt allowed bilingual switching; that carve-out
   has since been removed).

================================================================================
SECURITY / SAFETY NOTES
================================================================================

- `lang` from the client is never interpolated raw. The `=== "ar"`
  whitelist means the only two possible strings that reach buildPrompt
  are the literals "ar" and "en", both hard-coded in the source.
- The FORMAT section of the new prompt explicitly forbids revealing or
  summarising the prompt and forbids taking on another persona; combined
  with the whitelist above, this closes the two obvious prompt-injection
  vectors on this endpoint (locale field, message content).
- No changes to rate limiting, message clamps, or the Upstash key
  format — abuse posture is unchanged.

================================================================================
VERIFICATION
================================================================================

- `npx tsc --noEmit` runs clean after the changes (no new type errors).
- No other files reference SYSTEM_PROMPT, so removing it is safe.
- No behaviour change to the UI itself — the widget still renders,
  scrolls, and sends messages exactly as before; only the request body
  gained a `lang` field and the server-side prompt was replaced.

FOLLOW-UP: EXPANDED LINK WHITELIST (same day)
================================================================================

Goal: let Nollie point visitors at more than just the contact form.
Added targets: #portfolio, /guides/website-cost-in-egypt, and the
#pricing-calculator anchor inside that guide (rendered at
app/components/utils/PricingEstimator.tsx:133).

Files touched
-------------
- app/components/chat/ChatWidget.tsx  — new whitelist + renderer.
- app/api/chat/route.ts               — prompt updated to teach the
  model about the new targets and drop the old "cannot link" lines.

app/components/chat/ChatWidget.tsx
----------------------------------
- Removed the single-purpose CONTACT_LINK regex.
- Added a `LINK_TARGETS` Set with the four legal markdown targets:
    "#contact"
    "#portfolio"
    "/guides/website-cost-in-egypt"
    "/guides/website-cost-in-egypt#pricing-calculator"
- Added a broader `MARKDOWN_LINK` regex: /\[([^\]]+)\]\(([^)]+)\)/g.
  Two capture groups (label, target), so String.split yields triples
  [chunk, label, target, chunk, label, target, ...] which the renderer
  walks with `i += 3`.
- The renderer now:
    * emits the plain-text chunk (if any),
    * if the captured `target` is in LINK_TARGETS, renders an <a> with
      href = `/${lang}${target}` (same locale-prefix convention that was
      already used for #contact — works uniformly for pure anchors
      like "#portfolio" and for absolute paths like the guide URL),
    * otherwise re-emits `[label](target)` as literal text so a
      hallucinated / mistyped link does not become clickable garbage.
- The <a>'s onClick still calls onNavigate (which closes the widget),
  matching the original contact-link behaviour. For same-page anchors
  the browser jumps in place; for the guide URL Next.js does a full
  page navigation and the widget re-mounts fresh — either way, closing
  the panel is the right default.
- Styling unchanged: `text-gold-light underline underline-offset-2
  hover:text-gold`.

app/api/chat/route.ts — prompt edits
------------------------------------
Three surgical edits inside buildPrompt(); nothing else in the file
changed.

1. Pricing FACTS paragraph
   Before: "…on this site. Refer to it by name; you cannot link to it."
   After:  "…on this site — point visitors there whenever they ask
            about cost."
   Reason: the calculator anchor is now linkable, so instructing the
   model to only name it was actively wrong.

2. Portfolio FACTS paragraph
   Before: "You may mention that it exists, but you know nothing about
            any individual project."
   After:  "You may point visitors to it, but you know nothing about
            any individual project so do not describe them."
   Reason: same — mention -> point (link), while preserving the
   don't-describe-projects guardrail.

3. FORMAT section — link rules
   Before: a single "One exception: [phrase](#contact) is the only
            link that works on this site" sentence.
   After:  an enumerated allow-list of the four legal markdown
            targets, each with a one-line description of when to use
            it, plus explicit "never invent any other target" and
            "at most one link per reply" guardrails. The pricing-
            calculator entry is annotated as "the right target for
            any cost question" so cost queries land on the calculator
            instead of the guide's top.

Renderer/prompt contract
------------------------
- Any markdown target the model emits that is NOT in the widget's
  LINK_TARGETS set will show up as literal text `[label](target)`.
  The prompt now enumerates exactly those four targets and forbids
  inventing others, so the whitelist in the widget and the allow-list
  in the prompt are kept in lockstep. If either list is edited in the
  future, the other must be updated to match.

Verification
------------
- `npx tsc --noEmit` clean.
- No other files reference CONTACT_LINK, so renaming it to
  MARKDOWN_LINK / LINK_TARGETS breaks nothing.

FOLLOW-UP: LINK-EMISSION RELIABILITY, ESP. IN ARABIC
================================================================================

Symptom that triggered this
---------------------------
An Arabic reply to a cost question ended with the plain-prose phrase
"المزيد من المعلومات هنا" (literally "more information here") with no
markdown link syntax around it. The widget's regex had nothing to match,
so the phrase rendered as text. Root cause was purely on the model side:

  * All link examples in the prompt were English-only, so the model did
    not carry the [label](target) pattern over when it switched language.
  * The FORMAT rule "Use one where it genuinely helps" reads as
    permissive, so the model felt free to describe the destination in
    prose rather than link to it.
  * No explicit rule tied the language of the [label] to the language
    of the surrounding reply, so even when the model did link, an
    English label could sit inside an otherwise-Arabic sentence.

File touched
------------
- app/api/chat/route.ts — prompt-only edit inside buildPrompt(); no
  code changes.

Prompt edits (FORMAT section)
-----------------------------
- Replaced the "Use one where it genuinely helps..." sentence with a
  tighter block that:
    * Keeps the whitelist and the "never invent any other target" rule.
    * Adds an explicit "the target inside the parentheses is always
      the exact ASCII string below, never translated or transliterated"
      rule — so the model can't turn "/guides/website-cost-in-egypt"
      into an Arabicised path.
    * Adds a "the label inside [ ] must be in the same language as the
      rest of your reply" rule — English label in English replies,
      Arabic label in Arabic replies.
- Removed the annotation "the right target for any cost question" from
  the fourth list item and replaced it with a standalone paragraph:
    "Whenever the visitor asks about cost, price, or how much a project
    costs, you must include the pricing-calculator link. Do not
    describe the calculator in prose alone."
  Wording upgraded from soft ("the right target") to mandatory ("must
  include"), and applied to a broader trigger set (cost / price / how
  much).
- Added a "Worked examples of the link syntax in both languages" block
  showing both an English and an Arabic reply that use the pricing-
  calculator link correctly. The Arabic example uses "حاسبة الأسعار"
  as the label and the ASCII target unchanged, modelling both new
  rules at once.

Contract with the widget
------------------------
Unchanged. The widget's LINK_TARGETS Set still holds exactly the four
ASCII targets. The new prompt rules just make it much more likely that
the model actually emits one of them, in the right language, when it
should.

Verification
------------
- `npx tsc --noEmit` clean.
- No code paths changed; behaviour change is entirely in the model's
  output distribution.

================================================================================
FOLLOW-UP: COLLAPSED ROUTING RULE — REMOVED GENERAL-KNOWLEDGE CARVE-OUT
================================================================================

Motivation
----------
The prompt had two adjacent sections whose jurisdictions overlapped:

  WHEN YOU DO NOT KNOW           — "not in FACTS → offer the team"
  GENERAL WEB DESIGN QUESTIONS   — "you may answer from your own
                                    knowledge if you hedge"

Any web design question the visitor asked fell into both at once. The
model had to choose between them each turn, and the hedged carve-out
consistently won because it let the model be more helpful in the
short term. Net effect: general-knowledge answers leaking into what
was supposed to be a lead-capture bot, occasionally in a tone that
could read as an implicit studio commitment.

File touched
------------
- app/api/chat/route.ts — prompt-only edit inside buildPrompt(); no
  code changes.

Prompt edits
------------
1. Deleted the entire GENERAL WEB DESIGN QUESTIONS section.
2. Replaced the WHEN YOU DO NOT KNOW section with a single merged
   section titled WHEN THE ANSWER IS NOT IN FACTS. The new section:
     * Establishes FACTS as the only source the model may state from,
       and forbids answering from own knowledge "not even hedged with
       'generally'" — closing the loophole the old carve-out opened.
     * Uses a live [the contact form](#contact) markdown link inside
       the prompt, both to teach the pattern and to be the canonical
       fallback destination.
     * Enumerates, without exception, the three question classes that
       must be deflected: specific-feature/technology capability
       questions (with worked examples — WordPress, Shopify, Paymob,
       payment gateways, booking tools), general web-design advice
       and comparisons, and non-listed policy/discount/quote/date
       questions.
     * Names cost as the one carved-out exception, routed to the
       pricing calculator link per the FORMAT section — so cost
       questions still land on the calculator rather than being
       generically deflected to the contact form.
     * Preserves a narrow safety-valve: a one-sentence bare
       definition of a term already used in FACTS (e.g., SEO, admin
       panel) is allowed, since a bare definition cannot be mistaken
       for a capability claim. Without this, "what is SEO?" — a
       term FACTS itself uses as an add-on name — would deflect to
       the contact form, which reads as broken rather than careful.
3. Removed the now-redundant sentence "Discount requests, firm
   quotes, and questions about specific features or technologies all
   go to the team" from the old WHEN YOU DO NOT KNOW paragraph — the
   new section is now the single source of truth for routing rules,
   avoiding the two-jurisdiction problem returning through the back
   door.

Expected behaviour shift
------------------------
- Narrower useful surface: FACTS + the four whitelisted links + bare
  term definitions.
- More deflections to #contact for feature/technology/opinion
  questions; more deflections to the pricing calculator for cost
  questions.
- If chat logs later show deflection on things FACTS could plausibly
  answer, the correct fix is to grow FACTS (e.g., add a line about
  which payment integrations are in scope), not to reintroduce a
  general-knowledge carve-out.

Widget-side dependency
----------------------
The new section leans on the pricing-calculator link existing in the
FORMAT whitelist and being reachable via the widget's LINK_TARGETS
Set. Both are already in place from the earlier follow-ups. If any
other guide is added later ("what to prepare before your project",
etc.), it must be added to both the FORMAT whitelist and the widget's
LINK_TARGETS before it can safely be routed to from here.

Verification
------------
- `npx tsc --noEmit` clean.
- Section headings across the prompt are now: FACTS, WHEN THE ANSWER
  IS NOT IN FACTS, OFF-TOPIC, LANGUAGE, FORMAT.

FOLLOW-UP: LANGUAGE HARD-LOCK + OFF-TOPIC WORDING
================================================================================

Two small edits made directly to app/api/chat/route.ts (prompt-only,
inside buildPrompt()). No code paths changed.

1. LANGUAGE section rewritten as a hard lock
   Before (paragraph): "Answer in ${language}. If the visitor clearly
   writes in the other language, switch to theirs. If they write
   Arabic using Latin letters, answer in Arabic script. Write Modern
   Standard Arabic, never colloquial. Keep English technical terms
   such as SEO, CMS and WhatsApp, and the name SM Web Studio, in
   Latin letters. Never answer the same question twice in two
   languages."
   After: "Answer only in ${language}. When ${language} is Arabic,
   write Modern Standard Arabic, never colloquial."

   Effect: the earlier design was locale-biased-but-visitor-can-
   override. The new design is locale-locked — an English-page
   visitor who types Arabic will still receive English back, and
   vice versa. Route awareness now fully determines reply language.
   The DATA FLOW section above has been updated to reflect this;
   the earlier claim that the visitor could override the locale is
   no longer true.

   Side effect of the rewrite: the earlier guidance about keeping
   English technical terms (SEO, CMS, WhatsApp, SM Web Studio) in
   Latin letters was dropped along with the rest of the paragraph.
   If Arabic replies start transliterating these terms into Arabic
   script, that guidance should be re-added as a standalone rule.

2. OFF-TOPIC wording softened
   "decline in one short sentence" → "decline politely in one short
   sentence". No semantic change — just a tone nudge.

Verification
------------
- `npx tsc --noEmit` clean.
